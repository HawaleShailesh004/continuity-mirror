### POST `/api/baselines`

Multipart field `image` (JPEG/PNG/WebP; HEIC is rejected with details.hint='heic'). Downsize to long side ≤ 1600 and ≤ 1.5 MB first. The server normalises to JPEG, long side 1024, EXIF stripped, and uploads to YouCam (free). baselineId = sha256 of the normalised bytes. 201 for a new baseline, 200 when reused. Kept 24 h.

### POST `/api/jobs`

Idempotent: the same baseline + spec returns the existing job (200) unless it failed; the same clientRequestId returns that request's job. Use a new clientRequestId for a retry after failure. Units are reserved on create and refunded when the job fails (YouCam errors are free).

### GET `/api/jobs/{id}`

Job ids are unguessable capability tokens (96-bit), so a job can be resumed even if the session cookie was lost. Polls within 4 s of the last check are answered from the server's cache; retryAfterMs is 2 s, 4 s after 30 s, 6 s when the YouCam call budget is exhausted. Jobs fail with YOUCAM_TIMEOUT after 180 s.

### POST `/api/shares`

Multipart: `meta` (JSON, CreateShareMeta, with `consent: true`) and `images` (one file per item, same order, ≤ 2 MB each, ≤ 4.4 MB total). Images are re-encoded to JPEG (≤ 1024 px, metadata stripped) and stored privately until the link expires or is revoked. 5 creates per hour per session. 403 FEATURE_DISABLED when shares are off (status.capabilities.shares).

### GET `/api/shares/{token}/items/{key}`

Streams the image through our server; storage is private. 410 once the link is expired or revoked.

### POST `/api/webhooks/youcam`

Verified with webhook-id / webhook-timestamp / webhook-signature (HMAC-SHA256, YOUCAM_WEBHOOK_SECRET, 5 min tolerance) and deduped by webhook-id. Treated as a nudge: only the task id is read from the body, and the job is advanced by asking YouCam (same path and lock as polling). 404 when no secret is configured.

## The core flow

1. `GET /api/status`: if `live` is false, offer sample personas only. `mode: "mock"` means results are not real.
2. `POST /api/baselines` (multipart `image`) → save `normalisedImage` and `baselineId` on the device. `normalisedImage` is a `data:` URL: decode it in the page (base64 → bytes → Blob). **Don't `fetch()` it**: the production CSP (`connect-src 'self'`) forbids that.
3. For each route: store a `clientRequestId` (uuid) on the device **before** sending, then `POST /api/jobs`.
4. Poll `GET /api/jobs/:id` every `job.retryAfterMs` until `status` is `succeeded` or `failed`.
5. When `resultReady`, immediately `GET /api/jobs/:id/result` and save the bytes (the upstream URL expires; 410 after ~110 min).
6. A failed job carries `error` (same `ErrorBody` as HTTP errors). To retry, send a **new** `clientRequestId`.

### Route jobs and colour

`spec.colour` decides the pipeline (see `lib/catalog/pipeline.ts`):

| colour.source | Template style | Reference style (e.g. coily) |
|---|---|---|
| `own` (hex from "tap your hair", or the family default) | hair-transfer → hair-color restore = **3 units** | hair-transfer with `hair_color: src` = **2 units** |
| `template` | hair-transfer = 2 units | hair-transfer = 2 units |
| `preset` | hair-transfer → hair-color preset = 3 units | hair-transfer → hair-color preset = 3 units |

`colour` jobs = 1 unit, `brows` jobs = 1 unit. Session cap 24 units by default (`status.session`), plus a per-IP daily cap (48). Units are reserved at create and refunded when YouCam rejects (its errors are free); a timeout keeps its reservation.

### Limits

All return 429 `RATE_LIMITED` with `Retry-After`: 150 API calls/min per session, 400/min per IP, 8 baseline uploads/min, 10 job creates/min, 5 share creates/hour. Votes: 5 per helper per share, 200 per share.
When the real YouCam balance drops below `UNIT_FLOOR` (150), `status.live` turns false (`reason: "units_low"`) and new jobs get 503 `LIVE_DISABLED`: offer the sample personas.

### Share links (P1)

Gate the UI on `status.capabilities.shares` (on by default locally, off on Vercel until configured).

1. Owner: `POST /api/shares` (multipart: `meta` JSON with `consent: true`, `items` (1–4 labels) and `expiresInDays` (1–7); `images`, one per item). Show `ownerKey` once and keep it on the device: it is the only way to see results or revoke, and we store only its hash.
2. Helper: opens `url` (`/share/<token>`), reads `GET /api/shares/:token`, shows each `imageUrl`, and votes with `POST /api/shares/:token/votes`. No account, no cookie needed.
3. Owner: `GET /api/shares/:token/results` with header `x-owner-key`; `DELETE /api/shares/:token` with the same header deletes images and votes immediately.
4. Unknown, malformed, expired and revoked tokens all answer 410 `EXPIRED` (a caller can't tell them apart). Notes and labels are plain text: render them as text, never as HTML.
5. Images are re-encoded (JPEG, long side ≤ 1024, all metadata removed) and held in private storage; `privacy/receipt.serverStoresImages` is true while the person has a live link. A daily cron (`/api/cron/cleanup`) deletes expired links and stray images.

## Mocks

Two mock layers, same scenarios:

- **MSW** (`lib/contracts/mocks/backend.ts`, `MockBackend`): the whole API in the browser or Node tests, no server needed. Results are genuine B0 YouCam outputs on the AI sample people.
- **The real server with `YOUCAM_MODE=mock`** (the default locally): every real route, with the YouCam adapter faked (`lib/server/youcam/mock.ts`). Results are your own photo with a large "MOCK" watermark. Share links are real here too (in-memory storage, lost on restart).

- **Browser:** `startMockWorker()` from `lib/contracts/mocks/browser.ts` (call it from a client component when `NEXT_PUBLIC_API_MOCKS=1`). URL switches `?mock=<scenario>` and `?mockLatency=0` are remembered; `window.cmMock.setScenario(...)` and `window.cmMock.reset()` from the console. State survives reloads (localStorage), so resume-on-reload can be tested.
- **Per request:** header `x-cm-mock-scenario: <scenario>` (also honoured by the server when `YOUCAM_MODE=mock`).
- **Fixtures:** `lib/contracts/mocks/fixtures.ts` (personas with snapshots, result images under `/mock/`).

| scenario | behaviour |
|---|---|
| `ok` | Everything succeeds with realistic latency |
| `slow` | Steps take 4× longer (≈ 50 s for a 2-step route); polls hint 4 s |
| `no_shoulder` | Jobs fail: YOUCAM_REJECTED / error_no_shoulder |
| `hair_too_short` | Jobs fail: YOUCAM_REJECTED / error_hair_too_short |
| `face_pose` | Jobs fail: YOUCAM_REJECTED / error_face_pose |
| `unavailable` | Jobs fail: YOUCAM_UNAVAILABLE (retryable) |
| `timeout` | Jobs stay running, then fail YOUCAM_TIMEOUT after 180 s |
| `rate_limited` | POST /api/baselines and /api/jobs → 429 RATE_LIMITED, Retry-After: 5 |
| `budget_exhausted` | POST /api/jobs → 403 SESSION_BUDGET_EXHAUSTED; status shows the cap reached |
| `live_disabled` | status.live=false (reason disabled); uploads and jobs → 503 LIVE_DISABLED |
| `partial_failure` | The new-chapter route fails once (retryable); a retry succeeds |
| `expired` | Results → 410 EXPIRED |
